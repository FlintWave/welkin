## 1. Review of the LLSD design should verify

For a PBR material LLSD payload, check these invariants:

- **Schema versioning**
  - There is an explicit `version` key or documented implicit version.
  - Unknown/future versions fail safely or are ignored, rather than crashing.
  - Round-tripping preserves unknown keys where appropriate.

- **Texture binding slots**
  - Each texture slot has a stable identifier (`base_color`, `normal`, `metallic_roughness`, `emissive`, `occlusion`, etc.).
  - Missing textures are distinguishable from null/empty UUIDs.
  - Texture transform fields (offset, scale, rotation, UV set) are documented and typed.

- **Factor ranges**
  - Metallic, roughness, alpha cutoff, emissive intensity, etc. are range-validated.
  - Defaults match viewer/runtime defaults.
  - Out-of-range LLSD values are clamped or rejected consistently.

- **Alpha mode**
  - `OPAQUE`, `MASK`, `BLEND` are enumerated constants, not raw strings scattered through code.
  - `alphaCutoff` is only meaningful in `MASK` mode.

- **Color/factor typing**
  - Colors are consistently arrays of floats or ints, with defined channel count.
  - sRGB vs linear usage is documented.
  - UUIDs are stored as strings/UUIDs consistently, not mixed.

- **Material identity**
  - Material ID/asset ID vs. local wearables index is separated.
  - Wearable layer vs. body/face material slot is unambiguous.
  - LOD/baked/unbaked material paths are not conflated.

- **LOD / avatar feature gating**
  - “Modern avatar features” often needs capability checks: PBR support, baker support, attachment support, baked texture generation.
  - LLSD must not assume a feature is available just because the key exists.

- **Serialization symmetry**
  - Parse/build use the same key constants.
  - Default material objects generate the same LLSD as parsed default objects.
  - Golden LLSD fixtures exist for regression testing.
