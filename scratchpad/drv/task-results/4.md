Suggested smoke tests for weather day-cycle binding in a script VM (minimal, end-to-end sanity checks):

1. **Basic bind + read**
   - Initialize VM with a weather provider and day-cycle source.
   - Load a script that reads the bound weather state.
   - Invoke it at known times: `00:00`, `06:00`, `12:00`, `18:00`.
   - Pass: returns a valid weather object/value for every time; no exception; VM remains runnable.

2. **Day-cycle advancement**
   - Bind weather to day cycle.
   - Evaluate weather at time T0.
   - Advance day cycle to T1.
   - Evaluate again.
   - Pass: result changes or updates according to provider logic (or stays deterministically equal if expected), without stale cached values.

3. **Default/unbound behavior**
   - Start VM without a weather provider or without binding.
   - Run script that references weather binding.
   - Pass: resolves to documented fallback/default/no-op value, or throws the documented binding error; VM does not crash.

4. **Callback/event delivery**
   - Register script callback on binding updates.
   - Advance day cycle one tick.
   - Pass: callback fires exactly once with expected time/weather arguments; no duplicate or missed events.

5. **Invalid input handling**
   - Invoke bound weather lookup with out-of-range/NaN/invalid time.
   - Pass: VM returns documented error/default instead of crashing or corrupting VM state.

6. **Rebind and teardown**
   - Bind provider A, evaluate, then rebind provider B and evaluate again.
   - Dispose VM/session.
   - Pass: after rebind, only B’s values are used; after dispose, binding callback no longer fires and no dangling references are observed.

7. **Determinism**
   - Run two identical VM instances with same weather/day-cycle inputs.
   - Pass: weather outputs match for corresponding times.

Potential pass criteria summary:
- No crashes/VM aborts.
- Bound values update with day cycle.
- Callback count and arguments match expected.
- Error cases are contained.
- Rebind/dispose behavior is clean.
